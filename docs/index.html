01

A model answers in two different phases

Almost every design decision in every engine below is a response to the gap between prefill and decode. They have opposite bottlenecks and they compete for the same GPU.

Why batching is the primary lever. The weights are read once per step, not once per sequence. Decode 32 sequences in one step and that same memory traffic produces 32 tokens instead of 1. Arithmetic intensity rises ~32× and so does throughput — which is the entire economic argument for a serving engine over a for loop.

02

The roofline: the speed limit you cannot argue with

A kernel is limited either by how fast the GPU does math or by how fast it moves bytes. Which side you are on determines which optimisations can possibly work. 

achievable FLOP/s = min( peak_FLOPs , arithmetic_intensity × peak_bandwidth )
                         \______/                              \___________/
                       compute roof                            memory roof
Where each phase sits on the roofline

How to use this. Everything left of the ridge point is bandwidth-starved: the only wins are moving fewer bytes — quantization, kernel fusion, a smaller KV cache, bigger batches. Faster arithmetic (FP8, better tensor-core use) does nothing there. Notice that the ridge barely moves from a T4 to an H100 while raw performance grows ~15×: memory bandwidth has not kept pace with arithmetic, and that divergence is why inference engineering is almost entirely about moving fewer bytes.

03

The KV cache is your real memory budget

Weights are a fixed cost. The KV cache is the variable one, and it — not the model size — decides how many users you can serve at once. 

KV bytes = 2 (K and V) × layers × kv_heads × head_dim × tokens × dtype_bytes
How many sequences fit, by context length

Why grouped-query attention exists

Notice the kv_heads term. Qwen2.5-0.5B has 14 query heads but only 2 KV heads — each KV head is shared across 7 query heads. That makes the cache 7× smaller than plain multi-head attention, which translates directly into 7× more concurrent users in the same memory. Try switching models above and watch the per-sequence cost change far more than the parameter count does.

Six ways an inference benchmark lies.

1. No warmup — the first request pays for CUDA context, autotuning and graph capture, and can be 10× the steady state.
2. The client is the bottleneck — check with Little's Law: throughput × latency should equal the concurrency you requested.
3. Different output lengths — without ignore_eos you are measuring verbosity, not speed.
4. "Tokens/s" without saying which — counting prompt tokens makes summarisation look 10× faster than chat on identical hardware.
5. Closed-loop only — workers that wait for a response back off automatically, so the server can never fall behind and you never find the cliff.
6. Comparing default configs — SGLang caches prefixes by default; vLLM has not always. That is a flag comparison dressed up as an architecture comparison.

05

Three generations of batching

Encoders need one forward pass per request; decoders need hundreds, and each request finishes at a different time. That difference produced three distinct scheduling designs.

No batching

One request at a time. The GPU is ~99% idle during decode. This is a transformers loop, and it is the baseline every engine is measured against.

Dynamic batching

Wait up to max_queue_delay, group whatever arrived, run it to completion. Correct for encoders — one pass per request. This is Triton Inference Server's scheduler.

Continuous batching

Rebuild the batch every decode step; members join and leave mid-flight. Required for decoders, where requests need wildly different numbers of passes.

A common misconfiguration. Putting Triton's dynamic batcher in front of an LLM backend adds queue delay ahead of a scheduler that already does something strictly better. For vLLM or TensorRT-LLM backends, leave dynamic_batching out of config.pbtxt.

06

Paged KV cache, and sharing prefixes

Two mechanisms that follow directly from the KV-cache arithmetic in section 03. Both are about not storing, and not recomputing, the same thing twice.

PagedAttention — virtual memory for the KV cache

RadixAttention — prefix sharing as a tree

vLLM hashes blocks: does this exact block of tokens already exist? SGLang keeps the cache in a radix tree keyed on token sequences, which additionally handles partial matches, nested matches, and branching — agent retries, beam search, self-consistency sampling all fork from a common ancestor.

Quantization: where the bits should go

Decode is bandwidth-bound, so making the weights smaller makes decode faster almost proportionally. The art is deciding which weights absorb the error.

Weight-only 4-bit transforms decode and does almost nothing for prefill — prefill was never waiting on weight bytes.

The result that surprises people. Round-to-nearest 4-bit quantization of roughly Gaussian weights has a floor of about 10% relative error, and that error does not average away in the matmul — signal and error both grow as √K, so the relative error is preserved. 4-bit models work not because the arithmetic error is small, but because trained transformers are robust to it. That is an empirical property, which is why quantization quality must be measured rather than assumed.

AWQ, GPTQ and llama.cpp's importance matrix all beat that floor the same way: not by rounding better, but by choosing which weights absorb the error.

08

The engines

Four engines and one serving layer. The most common mistake is treating Triton as a fifth engine — it is the thing that runs the others.

Inference engine

vLLM

  • PagedAttention, continuous batching, prefix caching, chunked prefill
  • Widest model coverage; usually supports new architectures first
  • Biggest ecosystem — most tooling assumes it
Choose when you want excellent throughput on an OpenAI-compatible API without compiling anything. The sane default.
Inference engine

SGLang

  • RadixAttention — prefix sharing as a tree, not a hash table
  • Zero-overhead scheduler: CPU work overlaps GPU compute
  • Fast grammar-constrained output; a frontend DSL for multi-call programs
Choose when prompts branch or share long prefixes: agents, multi-turn sessions, self-consistency sampling.
Inference engine

llama.cpp / GGUF

  • Runs on CPU, Apple Silicon, AMD, Intel — not just NVIDIA
  • Partial GPU offload: the model need not fit in VRAM
  • One static binary; the whole model in one file
Choose when there is no datacenter GPU, the model does not fit, or you are serving one local user.
Inference engine

TensorRT-LLM

  • Ahead-of-time compilation: fusion + autotuning for your exact GPU
  • Lowest TTFT and batch-1 latency on NVIDIA hardware
  • Engines are not portable; shape bounds are compile-time constants
Choose when latency is the product, the model is stable, and you have CI to manage engine artifacts.
Serving layer — not an engine

Triton Inference Server

  • Hosts many models and many frameworks behind one API, on one GPU
  • Dynamic batching for models that cannot batch themselves (encoders)
  • Ensembles and BLS keep a pipeline server-side; versioning, metrics, k8s
Choose when you have model variety, not just model scale. For one LLM and one framework it is overhead with no benefit.

Encoders are a different problem entirely

Half of real inference is classification, embedding and reranking. An encoder does one forward pass per request — no autoregressive loop, no KV cache. PagedAttention, continuous batching and prefix caching all become irrelevant, and TTFT/TPOT are undefined.

If the output comes from a fixed set — a label, a score, a vector — an encoder is probably right and is 10–100× cheaper. If the output is open-ended, you need a decoder. The mature answer is usually both: prototype with the decoder, distil into an encoder, keep the decoder for the long tail.

10

Which should you use?

Benchmarks go stale; the reasoning does not. Answer four questions.

Things that are true regardless of engine

  1. Your workload shape decides more than your engine choice. Turning prefix caching on or off moves TTFT more than any engine-vs-engine difference at matched settings.
  2. Quantization is usually the biggest single lever, and it is engine-independent.
  3. Deploy at the goodput peak, not the throughput peak. They are different concurrencies, and the gap is where "great benchmark, unhappy users" lives.
  4. Measure your own prompt distribution. Every number on this page is specific to one model, one GPU and one set of lengths.

Making one faster: how to pick the kernel

The part people skip. Three questions, in order — skipping any of them is how a week goes into making something 3× faster that was 2% of runtime.

The worked example

Profile a decode step on a small model and the budget is dominated by linear layers. At batch 1 those are not matmuls at all — they are matrix-vector products at ~1 FLOP/byte, already running near peak bandwidth. cuBLAS is doing fine; there is no tuning win. The only lever is fewer bytes, so notebook 08 writes a fused int4 dequantize-and-multiply kernel in Triton: 

fp16 weights:  K × N × 2 bytes
int4 weights:  K × N / 2  +  2 × (K/128) × N × 2    →  ~3.8× less traffic

The dequantized values never touch HBM — they exist only in registers. A version that dequantizes into a buffer and then calls cuBLAS is slower than fp16, because it moves all the original bytes plus the int4 ones. Fusion is not an optimisation here; it is the entire point.

Try things in this order, highest expected value first: batching and scheduler config (free, usually the biggest win) → quantization (hours, 2–4× on decode) → prefix caching if the workload shares prefixes (free when it applies) → a different engine (days, modest factor) → custom kernels (weeks, targeted). Custom kernels are last because they are the most fun and the least leveraged — which is exactly why it is worth knowing how to tell when you have genuinely reached that point.
